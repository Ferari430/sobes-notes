Мапа в го это указатель на hmap
Поэтому если мы передаем мапу в функцию и что-то внутри этой мапы меняем, то в оригинальной мапе тоже будут изменения. Потому что мапа это ссылочный тип данных (Под капотом ссылается на структуру hmap).  (map_with_function_1)

Но если мы передаем мапу в функцию и в этой функции мапе переприсваиваем новую мапу, то тогда оригинальная мапа не изменится. Потому что в функцию передается копия указателя мапы. Оригинальная мапа не изменится. (map_with_function_2)

 При make(map[int]int) создается мапа с минимум 1 бакетов. При передаче n в make не создается n бакетов, создаемся как минимум n мест для n значений в мапе.\

# Устройство бакета:
 ![Screenshot from 2025-12-17 10-23-01](../../attachments/Screenshot%20from%202025-12-17%2010-23-01.png)
 Бакет это массив  из 8 элементов.  
 ![Screenshot from 2025-12-17 10-32-00 1](../../attachments/Screenshot%20from%202025-12-17%2010-32-00%201.png)
 
 Решетки это topHash из структуры bmap
 ![Screenshot from 2025-12-17 10-33-13](../../attachments/Screenshot%20from%202025-12-17%2010-33-13.png)
 ![Screenshot from 2025-12-17 10-36-30](../../attachments/Screenshot%20from%202025-12-17%2010-36-30.png)
 В памяти сначала лежит 8 tophash потом 8 ключей и затем 8 значений.
 Это нужно для того чтобы в кэш-линию быстро загружать нужные элементы. Так же нужно для того чтобы экономить память - тут пользуемся концепцией выравнивания.

Предназначение topHash:
Когда мы попадаем в бакет, мы не сравниваем сразу ключи. У каждой записи  в бакете есть свой topHash - это старшие 8 бит большого hashа. 
То есть это просто оптимизация для быстрого поиска ключа в бакетах.

При лоадФакторе = 6,5 происходит эвокуация. Она происходит не сразу а инкреминтально. То есть перенос из старых бакетов в новые происходит только при записи и удалении ключей (за один вызов может перераспределиться несколько старых бакетов в новые).

Приемущества такого подхода заключаются в том что нагрузка из-за эвокуации не становится слишком большой в моменте. Но при этом в процессе эвокуации запись и удаление новых объектов будет медленнее, а при поиске придется проверять  и новые и старые бакеты.

Словари в го:
1. Не хранят данные, отсортированные по ключу
2. Не сохраняют порядок, в котором были добавлены
3. Тип ключа словаря должен быть сравниваемым
4. При итерации порядок не определен

Почему при итерации не определен порядок по мапе?
-Чтобы разработчики никогда не основывались на то что порядок в мапе определен. 
Если в следующих версиях поменять порядок с определенного на неопределенный, чтобы код не ломался.

Как можно реализовать упорядоченное хранение данных в словаре?
Можно использоваться бинарное дерево поиска. В каждом элементе лежит ключ-значение. Но поиск будет медленнее - О(log n)
