---

Стэк и куча - это модели, которые определяют то, как мы организовываем и упправляем памятью. 
В учебниках по архитектуре было принято говорить, что куча распологается в начале пространства памяти, а стэк - в конце. Возможно, размещения стэка в конце можно объяснить принципом LIFO - последний пришел и первый вышел, получается что стэк растет снизу.

Стэк и куча растут друг к другу на встречу. Предположим что в какой то момент две организации памяти встретятся, чего допускать нельзя. Такая ситуация называется stackOverFlow. Чтобы не допустить такой ситуации, в памяти выделяется защищенная область - ProtectedArea.


| Параметр   | Куча                                                                | Стэк                                                    |
| ---------- | ------------------------------------------------------------------- | ------------------------------------------------------- |
| Скорость   | Медленнее                                                           | Быстрее                                                 |
| Чистка     | Медленная (GC)                                                      | Быстрая(Auto)                                           |
| Переменные | Хранит долго-живущие переменные (есть ссылки на объект вне функции) | Хранит временные переменные (переменные внутри функции) |
|            |                                                                     |                                                         |
В го каждой горутине выделяется свой стэк. Общение между стэками происходит за счет каналов.

Базовый размер стэка - 2кб. Растет до 1Гб в 64 битной системе и до 256 в 32 битной системе. 

## Работа стэка - увеличение
```go
func main() {
foo()
}

func foo() {
bar()
}

func bar() {
}
```
Предположим есть функции foo and bar которые вызываются в main. 
На самом деле в го аллоцируются так же и функции (в стеке main горутины), которые размещаются в стеке.

Функция в стэке представляет собой functionFrame. Который имеет три поля:
1. Адрес где функция завершится
2. Адрес предыдущего фрейма
3. Локальные переменные которые были созданы внутри функции.

Предположим что в bar аллоцируем массив который больше чем стандартный размер стэка 2кБ. 
```go
func main() {
foo()
}

func foo() {
bar()
}

func bar() {
	arr := [2100]byte{}
}
```

Рантайм видит что функция не влезает в стэк. Тогда рантайм выделяет новый кусок памяти (выделяет дополнительную память). Все вызванные до этого функции (main и foo)  копируются  в новый увеличенный стэк (старый при этом чистится), и так же добавляется новая функция.
В конце работы функции stack Frame чистится и стэк очищается от занятой в нем функции. 
```go
func main() {
a := 1
println("before", &a)

foo()
println("after ", &a)

}

func foo() {
bar()
}

func bar() {
arr := [100000]byte{}
println(arr)
}
```
По логике тут а должна поменять адрес памяти, так как го выделяет новый участок на стэке, но удивительно - этого не происходит, адрес а остается тот же самый. 
Объяснить это можно либо тем, что го заранее может выделять бОльшие объемы памяти для некоторых функций, либо адрес памяти совпадает с предыдущим потому что го выделил сам стэк по похожему адресу памяти.
## Работа стэка - уменьшение
Рассмотрим ситуацию, при которой стэк уменьшается.  
Логично предположить, что в момент когда функция завершает свое выполнение - стэк поинтер сдвигается назад к адресу предыдущего фрейма какой то функции. 
Но! Стэк в этот момент не чистится. 
![Screenshot from 2025-11-06 04-56-31](../../attachments/Screenshot%20from%202025-11-06%2004-56-31.png)
```go
func main() {
foo()
}

func foo() {
bar()
baz()
}

func bar() int {
b := 10
return b
}

func baz() int {
c := 20
return c
}
```
Новая ситуация - добавили функция baz которая вызывается в foo. Картинка сверху - в момент когда bar завершился, стэк фрэйм не чистится, а помечается специальным образом.
![Screenshot from 2025-11-06 05-00-50](../../attachments/Screenshot%20from%202025-11-06%2005-00-50.png)
Вызываем baz и в этот момент область памяти выделанная под inavlid memory очищается. Это место затем занимает baz. 
И вот проблема: сначала в стэк фрэйме была переменная b а затем ее затерла переменная с. Такую проблему решает механизм анализа побегов - он просто перемещает b в кучу. 

Вопрос: можно ли узнать где будет аллоцирована переменная, на стеке или на куче. Решение принимает компилятор. Он все старается разместить на стэке, но если невозможно доказать будет ли использована переменная где то снизу по коду, то просто переносит переменную на кучу.  

Нестрогие правила механизма анализа побегов (ЛУЧШЕ НЕ ОБСУЖДАТЬ):
1. Если функция возвращает ссылку на переменную то аллокация будет на куче.
2. Если объект слишком большой то он аллоцируется в куче.
3. Если значние переменной передается в функцию которая принимает interface то такая функция ВОЗМОЖНО будет аллоцирована в куче
4. Внутренние поля структр аллоцируются в куче (например массив от слайса)

Есть ли смысл где аллоцировать переменную для разработчика? 
-Есть, в куче работает GC и его вызов дорого стоит по памяти.
В чем проблема передачи переменной в функцию по значению (не по ссылке,указателю)?
-В том что такие переменные будут создаваться на стэке, и каждый раз копировать такие переменные дорого. (Sync.Pool)
Нужно ли вообще заморачиваться над всем этим?
-Если программа работает и так быстро (смотрим через профилирование pprof), то не стоит ее ускорять до предела. Если видим какие то утечки, то можно и подумать.
