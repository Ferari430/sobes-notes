Доступ к элементу хэш-таблицы (в Go это `map`) происходит за **O(1)** в **среднем случае** благодаря **хэшированию**. 
[[Что такое topHash в бакетах в мап го]]
---

В Go `map` реализован как хеш-таблица, содержащая массив бакетов.  
Каждый бакет может хранить **до 8 элементов** — то есть до 8 пар _ключ–значение_.  
Это фиксированная величина: 1 bucket = 8 слотов.

Внутри каждого бакета также есть **массив из 8 значений tophash** — по одному для каждого слота в бакете.

`tophash` вычисляется при вставке пары _ключ–значение_ и записывается в соответствующий слот бакета. Для каждой пары он **свой собственный**, т.е. tophash[i] соответствует key[i]/value[i].

`tophash` — это **верхний байт 64-битного хэша**, то есть всего **1 байт** (значение 0–255).  
Go использует этот байт как быстрый фильтр для поиска.

Это позволяет:

- перед сравнением ключей выполнить очень быструю проверку по `tophash`,
    
- не сравнивать ключи в тех слотах bucket, где tophash точно не совпадает,
    
- значительно ускорить поиск, особенно для строковых ключей, которые дорогие для сравнения.

 Также в структуре мапы в го есть указатель на  overflowed bucket. Всего вмещается 8 пар ключ-значение. Если хотим записать 9 элемент в такой бакет, то overflowed ptr перестает быть равен nill  и фактически к бакету присоединяется новый бакет (указатель на новый бакет передается в overflowed ptr).  Есть проблема, когда один бакет превращается в связный список и поиск идет уже в глубину а не в ширину.
 Фактически это означает, что мы не достигнем эваукации данных. Потому что коэффициент эвокуации в старой мапе = 6,5.

Зачем создали новую реализацию мапы через swiss table? 
Процессор подгружает в памяти ключи не по одному а пачкой - кэш-линией. Вполне вероятно что в кэш-линию сразу попадут все 8 ключей бакета (она большая), и казалось бы - если подгружены все ключи то сравнение полнученного из вне ключа будет происходить быстро со всеми 8 ключами. Но процессор работает ассинхронно. Это означает что он может переключаться между задачами, а для этого необходимо выгрузить всю кэш-линию на новую. Получается, что при первом неудочном сравнении полученного ключа с тем что в бакете может выгрузиться кэш-линия, что сильно замедляет работу мапы(Кажется что это проблема процессора а не мапы.).

Теперь бакетов нету! 
[New map in go by Swiss Table](../../../New%20map%20in%20go%20by%20Swiss%20Table.md)
Теперь **бакетов нет** — вместо них используются **группы**.  
В одной группе хранится **16 элементов** (16 пар ключ–значение).

Каждый ключ проходит хеш-функцию, и результат (64-битное число) разбивается на две части:

- **H1** — старшие 57 бит  
    Используются для выбора группы и пробирования.
    
- **H2** — младшие 7 бит  
    Используются как _fingerprint_ для быстрого отбора слотов внутри группы.
    

`H2` дополняется до полноценного байта (8 бит) одним **флажком занятости** (occupied flag).  
Этот байт — **метаданные слота**.

В каждой группе хранится массив из 16 таких байтов:

`[M1, M2, M3, ..., M16]`

Когда приходит новый ключ, его `H2+flag` сравнивается **одной SIMD-инструкцией** сразу со всеми 16 метаданными группы.

Результат — **маска из 16 позиций**, например:

`[0, 0, 0, 1, 0, ...]`

Это означает, что **4-й элемент группы — кандидат** для проверки.  
Если в маске есть 1 — сравнивается ключ.  
Если нет — пробируем в следующую группу.

Как происходит вставка элемента в группу:
Точно так же вычисляется группа в которую хотим вставить элемент. Далее по H2+bool вычисляется есть ли места в группе.
Если места нет - то идем в следующую группу. Это так же оптимизация - теперь мапа расширяется строго горизонтально и нет теперь связных списков из бакетов.

Note: В мапе количество таблиц это всегда 2 в степени n. Нельзя в мапе просто взять и добавить некоторое количество ГРУПП. Значение дискретно. 
Чтобы получить бОльшую мапу, необходимо ее отдельно аллоцировать и перенести туда данные из старой мапы, это называется эвакуацией.

# 🧩 Что такое map в Go

`map[K]V` — это **хеш-таблица с бакетами** (buckets), где ключи распределяются по бакетам через хеш-функцию.

---

# 📌 Основные структуры

## 1) **hmap** — главная структура словаря

Внутри runtime каждая map представлена структурой `hmap`:

- `count` — количество элементов
    
- `B` — степень таблицы (в таблице 2ᴮ бакетов)
    
- `buckets` — массив бакетов
    
- `oldbuckets` — массив старых бакетов (используется при расширении)
    
- `noverflow` — число overflow-бакетов
    

## 2) **bucket** — контейнер для нескольких пар key/value

Каждый bucket содержит:

- **8 слотов ключей**
    
- **8 слотов значений**
    
- **8 "tophash" байтов** — первые 8 бит хеша каждого ключа
    
- указатель на **overflow bucket**, если 8 слотов заняты
    

Таким образом, каждый bucket может хранить **до 8 элементов**, без расширения массива.

---

# 🔑 Как вставляются ключи (insert)

1. Вычисляется хеш от ключа.
    
2. По хешу выбирается bucket:
    
    ```
    bucket_index = hash & (2^B - 1)
    ```
    
3. В bucket записывается:
    
    - tophash: hash >> 56
        
    - ключ
        
    - значение
        
4. Если все 8 слотов заняты — создаётся **overflow bucket**.
    
5. Если overflow-бакетов становится слишком много → запускается **увеличение таблицы**.
    

---

# 🔍 Как работает поиск (lookup)

1. Вычисляется хеш ключа.
    
2. Находится bucket по маске.
    
3. В bucket:
    
    - сравниваются tophash'и (быстро)
        
    - если совпало — сравнивается ключ (медленно)
        
4. Если не нашли — переход в overflow bucket.
    

Средняя сложность: **O(1)**.

---

# 🧹 Удаление (delete)

При удалении:

- слот обнуляется
    
- tophash становится `empty`
    
- count уменьшается
    

Map **не сжимает бакеты** — только растёт, но overflow со временем исчезают.

---

# 📈 Когда и как происходит расширение (grow)

Go map растёт **в два раза**, если:

### 1️⃣ число элементов > 6.5 * количество бакетов

(порог load factor ≈ 6.5)

### 2️⃣ overflow бакетов становится слишком много

(признак коллизий и плохой распределённости)

### Реальный grow — _инкрементальный_

Когда таблица растёт:

- создаются новые бакеты в 2 раза больше
    
- `oldbuckets` указывает на старый массив
    
- при первой операции в конкретном старом bucket его элементы **переносятся** в новый (evacuation)
    

Это называется **incremental rehashing**  
→ нет больших пауз  
→ производительность стабильная

---

# 🔒 Конкурентный доступ запрещён

`map` **не thread-safe** — одновременная запись/чтение приводит к panic.  
Используют:

- `sync.Mutex`
    
- `sync.RWMutex`
    
- `sync.Map`
    

---

# 🚀 Оптимизации Go map

Go map использует множество хитростей:

- Inline top-hash для быстрого отбора кандидатов
    
- Cache-friendly размещение ключей/значений
    
- Incremental rehashing вместо полного
    
- Сравнение только по tophash перед сравнением ключей
    
- Размещение ключей и значений в разных массивах внутри bucket (эффективнее по кэшу)
