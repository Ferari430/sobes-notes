```sql
            END LOOP;  
    END;  
$$;
```

Создадим индекс по колонке content

```sql
CREATE INDEX hash_example_content_idx on hash_example USING hash (content);
```


```sql
select * from hash_example where content = 'ккцфслкфвруьутьил еквряымеиккулцкыиыуикртрцаискыл';
```

С индексом:

```sql
	Index Scan using hash_example_content_idx on public.hash_example  (cost=0.00..8.02 rows=1 width=99) (actual time=0.013..0.014 rows=1 loops=1)
"  Output: id, content"
  Index Cond: (hash_example.content = 'ккцфслкфвруьутьил еквряымеиккулцкыиыуикртрцаискыл'::text)
  Buffers: shared hit=3

  Buffers: shared hit=15
Planning Time: 0.091 ms
Execution Time: 0.024 ms

```

| Метрика                 | **БЕЗ индекса** (Seq Scan)  | **С индексом** (Hash Index) | **Разница**              |
| ----------------------- | --------------------------- | --------------------------- | ------------------------ |
| **Тип доступа**         | Полное сканирование таблицы | Сканирование по индексу     | -                        |
| **Стоимость (cost)**    | 0.00..2864.00               | 0.00..8.02                  | **в 357 раз дешевле**    |
| **Время выполнения**    | 4.526 ms                    | 0.024 ms                    | **в 189 раз быстрее**    |
| **Чтение буферов**      | 1614 buffers                | 3 buffers                   | **в 538 раз меньше I/O** |
| **Отфильтровано строк** | 99999 лишних строк          | только нужная               | -                        |
|                         |                             |                             |                          |
Коротко: пропускаем значение из запроса через функцию, получаем хэш --> получаем индекс в который нужно сходить и взять TID. Берем адрес и идем смотреть в таблице нужное значение.

Hash индекс дает колоссальный прирост к скорости только если значение в строке состоит из большого количества букв! Иначе хоть b-tree и будет весить больше, но будет отдавать ответ быстрее чем hash. 

---


Когда стоит смотреть в сторону хэш-индекса: когда надо экономить память, когда в селекте будет точное сравнение.
Когда не стоит смотреть в сторону хэш-индекса: когда сравнение не точное (не через =), а например частичное через LIKE.
