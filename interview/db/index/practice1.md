Создал таблицу 
```SQL
CREATE TABLE T(a integer,b text,c boolean);
```

Сделал вставку
```SQL
INSERT INTO t (a, b, c)
SELECT
    s.id,
    chr((32 + random() * 94)::integer),
    random() < 0.01
FROM generate_series(1, 100000) AS s(id)
ORDER BY random();

```

Первый запрос без индексов:
```SQL
explain (analyze , costs off ) select * from t where a = 1000;
```
Вывод:
```text
Seq Scan on t (actual time=3.452..3.745 rows=1 loops=1)
  Filter: (a = 1000)
  Rows Removed by Filter: 99999
Planning Time: 0.051 ms
Execution Time: 3.758 ms

```

Seq Scan - говорит о том что поиск идет построчно.

Добавим индекс.
```sql
create index on t(a);
```

Вывод:
```text
[2025-12-15 09:20:15] Connected
[2025-12-15 09:20:15] metrics.public> create index on t(a)
[2025-12-15 09:20:15] completed in 61 ms
```

Теперь запущу поиск с explain ещё раз:

Вывод:
```text
Planning Time: 0.308 ms
Index Scan using t_a_idx on public.t (actual time=0.012..0.012 rows=1 loops=1)
Execution Time: 0.040 ms
"  Output: a, b, c"
  Index Cond: (t.a = 1000)

```

 planning time - время за которое оптимизатор оценил оптимальный путь и запустил его
 execution time - время выполнения  всего запроса.
Оптимизатор принял решение сканировать по индексу.


В кратце как работает многоверсионность в постгресе:
```text
Когда я созадю запись в таблице у меня появляется новая строчка. Она актуальна.
Если я ее начну редактировать, то постгрес помечает эту строчку как неактуальную. Индексу надо понимать, он сейчас смотрит на старое или новое значение. Поэтому индекс сначала получает все данные, далее идет в таблицу и проверяет актуальные значения для данных и только тогда их печатает. Потому что индекс не имеет версионирования. Не понимает у него протухшие данные или свежие.
```

1. Vacuum удаляет все старые записи и все пустые строчки которые появляются при удалении старых значений. Оставляет актуальные значения. **VACUUM НЕ удаляет данные сразу. Он помечает место, занятое удалёнными строками, как "свободное для переиспользования".**
2. AutoVacuum делает это автоматически
3. VACUUM FULL принудительно очищает протухщие данные, но при этом таблица блокируется на запись , индексы перестраиваются - это опасно.

MVCC - это то самое версионирование данных, которое и пораждает протухшие и свежие данные. MVCC нужен для того, чтобы обеспечить параллельную работу транзакций над одними и теми же данными в таблице, что позволяет избегать блокировку при чтении одних и тех же данных.


Если в таблицу много раз вносили изменение - удаление или редактирование данных , то в таблице скапливается большое количество протухших версий данных. Индекс строится так же и на протухших данных, поэтому когда таких данных много - индекс замедляет свою работу.

Попробуем выполнить такой запрос:

```sql
explain (analyze , costs off ) select * from t where a < 100;
```

Вывод:

```text
Bitmap Heap Scan on t (actual time=0.080..0.333 rows=99 loops=1)
  Recheck Cond: (a < 100)
  Heap Blocks: exact=89
  ->  Bitmap Index Scan on t_a_idx (actual time=0.064..0.064 rows=99 loops=1)
        Index Cond: (a < 100)
Planning Time: 8.985 ms
Execution Time: 0.368 ms

```

Оптимизатор принимает решение сканировать по битовой карте. 

Потому что оптимизатор оценил, что **условие `a < 100` вернёт много строк**, и **читать таблицу по одной записи через индекс будет дороже**, чем:

1. **Сначала собрать все подходящие TID’ы в битовую карту** (`Bitmap Index Scan`)
    
2. **Потом прочитать heap-блоки пачками** (`Bitmap Heap Scan`)

Index Scan → «проходит дерево один раз, потом листовые страницы, потом обращение к heap для каждой строки».

Bitmap Heap Scan      [bitmap scan](../bitmap%20scan.md)→ «сначала строит bitmap из индекса, потом читает heap более эффективно, минимизируя random I/O».

 [селективность запросов](../селективность%20запросов.md)
- **Хороший запрос для индекса** — это **с высокой селективностью**, то есть возвращает мало строк относительно всей таблицы.
    
- **Плохой запрос для индекса** — низкая селективность, когда условие охватывает много строк: в этом случае последовательное сканирование таблицы (`Sequential Scan`) часто оказывается быстрее, чем обход большого диапазона индекса с множеством random I/O к heap.

При низкой селективности (900 подходит под запрос/1000элементов = 0,9) анализтор может принять решение искать строки с помощбю Seq Scan без использования индекса.

```SQL
explain (analyze , costs off ) select * from t where a < 40000;
```

```TEXT
Seq Scan on t (actual time=0.011..4.796 rows=39999 loops=1)
  Filter: (a < 40000)
  Rows Removed by Filter: 60001
Planning Time: 0.048 ms
Execution Time: 5.909 ms

```
