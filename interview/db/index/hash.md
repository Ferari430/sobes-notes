hash индексы - являются одностолбцовыми индексами, хранящими 32-битные результаты, полученные из значения индексированного столбца. Хэш-значение сопоставляется с сегментом, в котором хранится указатель на строку в таблице. (в индексе хранится хэш-значение и TID(УКАЗАТЕЛЬ на строку в таблице))

Тупая мысль: мы получаем значение из запроса и проводим хэширование, по результатам которого ищем индекс. Операции, обратной операции хэширование нигде не проводится, потому что такой операции вообще не существует! Хэширование - это односторонний процесс.

Hash-индекс использует страницы четырех видов:

1. Метастраница -  нулевая страница, содержащая информацию о том, что находится внутри индекса
2. Страницы корзин (bucket page) - основные страницы индекса, хранят данные в виде пар "хэш-код - TID" (TID - указатель на строку)
3. Страницы переполнения (overflow bucket ) -  устроены так же, как страницы корзин, и используются в случае когда одной страницы не хватает
4. Страницы битовой карты (bitmap page) - в них отмечаются освободившиеся страницы переполнения, которые можно использовать для других корзин. (Это та же битовая карта но у нее задача не находить элементы по нескольким условиям. У нее задача указывать на то какие бакеты свободны а какие нет - эта штука не участвует в поиске по таблице как например в b-tree.)
```sql
select hashtext('test') as hashValue;  
-- детерминированное поведение у hashtext  
  
select mod (hashtext('test'),10) as bucketpointer;  
-- хэш индекс хранится в 3 бакете
```

Хэши хранятся отдельно, индексы хранятся отдельно.
1. По ключу вычисляем хэш-код
    
2. Находим номер бакета
    
3. **Читаем страницу этого бакета с диска**
    
4. Ищем в бакете наш хэш-код (может быть несколько из-за коллизий)
    
5. Для найденного хэш-кода берём **TID**
    
6. **По TID идём в основную таблицу** и читаем строку

То есть на странице где хранится индекс имеем хэш-код и TID.

Если в индексе есть коллизии, то есть по одному и тому же хэш-коду хранится две записи, то берем TID этих двух записей и идем смотреть по ним значения из таблицы. И в финале сравниваем уже запись в таблице с тем значением которое пропускалось через хэш-функцию.

**При коллизии сравнивается фактическое значение столбца в таблице с искомым значением.**  
Hash-индекс даёт нам **кандидатов** (TID), но финальная проверка всегда идёт **по реальным данным**.

---
Ограничения хэш-индекса:
1. Поддерживается только сравнение на равенство при выполнении запроса (это связано с применяемой структурой данных. Потому что хэш-функция всегда нам выдает детерминированный результат при пропускании через нее ключа.)
		==При применении hash индекса мы каждый раз даже из отсортированного набора данных будем получать хаотичные индексы - это свойство хэш функции.==
		==Именно поэтому поиск по диапозону в запросе  `>`, `<`, `BETWEEN` будет давать сбой, ведь мы потеряли изначальный порядок входных данных.==

2. Поддерживается только для ключа из единственного столбца
3. Не имеют возможности накладывать ограничение на уникальность (у хэш-функции возможны коллизии)

Приемущества по сравнению с b-tree:
1. Очень быстрое обновление 
2. Скорость чтения в 3 раза выше
3. Размер ключа
4. Размер хэш-индекса не влияет насколько селективным является значение ключа индекса 

Пусть  в таблице с 1_000_000 записей есть столбец текстового типа с длиной в 25 символов.
Сравним hash и b-tree индексы.
Получим что через hash индекс прирост скорости поиска составит 60-80%, при этом вес такого индекса меньше в 50 раз, нежели при использовании b-tree индекса.
