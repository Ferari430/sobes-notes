Две разные стратегии к оптимизации запросов:
1.  Короткий запрос (найти для юзера что-то) когда возвращается мало записей
2.  Длинные запросы, которые выдают count или большое количество записей для отчетности, где используется seq scan



---


**Селективность** — доля строк таблицы, удовлетворяющих условию WHERE.  
От неё кардинально меняется стратегия оптимизации.

---

### 🎯 **Высокая селективность (возвращается мало строк, <5% таблицы)**

**Цель:** максимально быстро найти нужные строки, минимизировать чтение с диска.

| Подход | Что делать |
|--------|------------|
| **Индексы** | Создавайте индексы по полям, участвующим в WHERE, JOIN, ORDER BY. B-tree — базовый выбор. |
| **Покрывающие индексы** | Включайте в индекс все необходимые поля (`INCLUDE`), чтобы получить Index Only Scan. |
| **Точные соответствия** | Для условий равенства (`=`) индекс работает идеально. Для диапазонов — тоже хорошо. |
| **Сортировка** | Если сортировка по индексированному полю, избегайте отдельной операции сортировки. |
| **LIMIT** | Всегда ограничивайте количество строк, если нужно только несколько. |
| **Подготовленные запросы** | Используйте prepared statements для повторного использования плана. |
| **Статистика** | Следите, чтобы статистика была актуальна (`ANALYZE`), иначе planner может ошибиться. |

**Важно:** индексы полезны, только если они реально используются. Проверяйте через `EXPLAIN`.

---

### 📉 **Низкая селективность (возвращается много строк, >10–20% таблицы или агрегаты)**

**Цель:** эффективно обработать большие объёмы, используя последовательное сканирование и параллелизм.

| Подход | Что делать |
|--------|------------|
| **Parallel Seq Scan** | Разрешите параллельное сканирование (настройка `max_parallel_workers_per_gather`). |
| **Увеличение work_mem** | Для сортировок, хеш-соединений, агрегаций выделите больше памяти, чтобы избежать сброса на диск. |
| **Материализованные представления** | Если отчёт выполняется часто, заранее рассчитайте и сохраните результат. |
| **Партиционирование** | Разбейте большую таблицу по ключу (например, по дате) и сканируйте только нужные секции. |
| **Индексы не помогут** | При низкой селективности индекс часто проигрывает seq scan из-за случайных чтений. Не создавайте лишних индексов. |
| **Агрегаты** | Для `COUNT`, `SUM` старайтесь использовать параллельные агрегаты. |
| **Аппроксимация** | Если допустима погрешность, используйте расширения (например, `hyperloglog` для приблизительного COUNT). |
| **Columnar хранение** | Для аналитики рассмотрите колоночные расширения (Citus, TimescaleDB в режиме сжатия). |

---

### ⚙️ **Общие принципы (применимы всегда)**

1. **Анализируйте план** — `EXPLAIN (ANALYZE, BUFFERS)` показывает узкие места.
2. **Обновляйте статистику** — `ANALYZE` после массовых изменений.
3. **Настройте параметры планировщика** — `random_page_cost`, `effective_cache_size`, `work_mem` под ваше железо.
4. **Избегайте функций на индексированных колонках** — они ломают использование индекса.
5. **Используйте типы данных с умом** — сравнение чисел быстрее строк.

**Итог:** стратегия определяется селективностью. Для малых выборок — индексы и быстрый доступ, для больших — последовательное сканирование и параллельная обработка.
